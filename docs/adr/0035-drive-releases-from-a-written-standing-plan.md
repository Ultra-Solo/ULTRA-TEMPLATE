# ADR-0035: Drive releases from a written standing plan

**Status:** Accepted · **Date:** 2026-10-20

## Context

[`.github/agents/release-cadence.agent.md`](../../.github/agents/release-cadence.agent.md) is this repository's own procedure for deciding what the next release is. It says what a cadence check must do, and it says what it must start from: "The standing plan is the prior" (line 17), and for a repository that has none, "the first check writes one: the live triggers, each with its pre-made response, and the standing state as of today" (line 19). It also names the failure that follows from not having one: "re-deriving an unchanged plan is a failure mode, not thoroughness".

No such plan existed. Neither did the decision log or the prediction ledger the same file's later steps append to and score, although the agent's own `description` promises it "keeps the prediction ledger and decision records honest". So every cadence check began by working out from scratch which triggers exist and what each would mean — the step the procedure explicitly calls a failure mode — and had nowhere to write what it concluded.

The evidence that this had a cost is in the release history. [ADR-0025](0025-prioritize-verified-foundation-before-capability-expansion.md) planned a milestone of A1–A5 for one release and shipped only A1 in v3.3.0; [ADR-0026](0026-remap-the-foundation-milestones-to-versions.md) remapped the rest across two releases; [ADR-0027](0027-ship-run-and-diagnose-before-the-browser-smoke-test.md) split B1–B4 again, and says why in its own words: "Planning the split from the start costs less than discovering it mid-release"; [ADR-0028](0028-run-the-browser-smoke-test-through-the-e2e-slot.md) then found B2's topology change was "a manifest entry" after all. Three successive re-scopings inside three days, with the estimate wrong in both directions — too large twice, then smaller than expected. What recurs is not the direction of the error but the fact that nobody could see the scope until a release was already open, because the plan existed only inside the release that was re-reading it.

That ledger is now closed, which is what forces the decision rather than merely advising it. A1 shipped in v3.3.0; A2r, A4r and A5 in v3.4.0; B1, B3 and B4 in v3.5.0; B2 in v3.6.0. Nothing in [ADR-0025](0025-prioritize-verified-foundation-before-capability-expansion.md) is open. Releases v3.6.1 through v3.13.3 added no capability the ledger planned — a runner image pin, MCP Streamable HTTP, the Node, Go and Python toolchain lines, agent adapters, and the move to Ubuntu 26.04. v3.13.1 through v3.13.3 were maintenance only. The component that decided what to build next has been running without an input since v3.6.0, and its output has been the maintenance stream that exhaustion produces.

## Decision

The live triggers, the response decided for each, the decision log and the prediction ledger are written down in `template/release-cadence.md`, and a cadence check starts from that file rather than re-deriving it. A trigger is added to it only when it is observed, and it carries a threshold with a number in it and a response chosen before it fires. A question whose cost is not measurable from here is not given an invented number: it gets a date at which it is decided, and the observation that lets it ship, and at that date it either ships or moves in the open, with the move appended to the decision log. That distinction is deliberate — the failure [ADR-0025](0025-prioritize-verified-foundation-before-capability-expansion.md) recorded was scope that appeared only once a release was already open, and a date that could be slipped silently would reproduce it. The date is a date and not a release number because the measurement: this repository cut nine minors in the fifteen days before the plan was written, so a named future minor arrives before any evidence about it can accumulate, and the target comes due ahead of its own justification. `template/cadence.test.mjs` holds the table's schedule inventory to the `cron:` lines in `.github/workflows/`, so a schedule cannot be recalled rather than read.

The plan lives under `template/` because it is about maintaining this template itself, like the maintenance notes beside it. Everything there is deleted when a project is initialized, so the plan reaches no adopter and changes no generated output — which is what lets it be added without a release of its own. A generated project's first cadence check writes its own plan, as the procedure's line 19 already directs. This record ships, because a decision that lives only in `template/` would be deleted along with the reasoning behind it.

## Alternatives considered

- **Leave the procedure to re-derive the plan at each check.** This is what has been happening, and the procedure names it as the failure mode it is: each check re-opens questions the last one settled, and the ledger stays empty because nothing writes to it. It also cannot detect a change, because with no prior there is nothing to compare against.
- **Keep the triggers in the cadence agent's own prompt.** The agent ships in every generated project, where a trigger table naming the pinned-tool manifest and the template's own release machinery would be confidently wrong: no adopter keeps those files. It would also put a maintainer's calendar in front of a project that has a different one, and the table would have to be edited in a file whose job is to state a procedure rather than a state.
- **Put the plan under `docs/`, beside the ADRs.** It ships, so an adopter would inherit triggers for workflows they do not run: one of the scheduled workflows in the table exists only in this repository and is removed at initialization, and the pinned-tool manifest is absent entirely from a `minimal` project. The maintenance notes under `template/` also already state the rule this case falls under: "Template-only changes with unchanged output need no release", and `docs/` is not template-only.
- **Give each deferred question a target release rather than a date.** This was written first, and it failed on its own numbers. With minors about a day apart, a named future minor arrives twenty-six days before the check that was supposed to supply its evidence, so the item comes due while the answer is still unobservable — a deferral that looks decisive. A date cannot get ahead of the observation the row names, because both are the same date.
- **Add a check for the plan's thresholds themselves.** A check can compare a schedule inventory against the workflow files, and `template/cadence.test.mjs` does. It cannot decide whether a tool being two releases behind is worth a release, or whether an adopter's request has become a scope decision, and a check that pretends to would fail on judgement rather than on fact. The one claim in the plan that a check *can* hold is the template's version, because a file already states it; that is a generated block in the plan, not a threshold.

## Consequences

- A cadence check has a prior to arbitrate, so it can report that nothing fired and name the next checkable dates, instead of producing a fresh analysis each time.
- Predictions now carry the date they become checkable, so the Brier terms in the procedure's step 0 have rows to score. Until 2026-10-26 none has resolved, and the plan says so rather than scoring an empty ledger as zero.
- The plan can go stale, and the test only catches one kind of staleness: a schedule added, removed or changed in a workflow without the table following it. A threshold that stops being the right number, a check date that passes, or a trigger that should exist and does not, is caught by reading, not by the build. The template's current version is the one figure in the plan the build does catch: it is a generated block, so it cannot disagree with the file that states it.
- The two questions [ADR-0025](0025-prioritize-verified-foundation-before-capability-expansion.md) deferred — a database, authentication or deployment profile, and automatic update pull requests — are decided at the 2026-11-17 check. If they have not fired by then, they move to the 2026-12-15 check with a decision-log entry naming what was missing, so a deferral is recorded where a reader can see it rather than discovered mid-release.
