# ADR-0050: Hold a diagram's route claim to the API contract

**Status:** Proposed · **Date:** 2026-11-07

## Context

ADR-0049 added the protocol this repository relies on to keep its one runtime story honest: the model is checked in CI like any other source, so a diagram that lies fails the build. The first view written under it lied, and every check passed.

`architecture/model/views.c4` narrated the move as `POST /api/tasks/{id}/move`. This repository serves no such route. The contract in `scripts/contract/openapi.json` declares five method-and-path pairs — `GET /healthz`, `GET /api/tasks`, `POST /api/tasks`, `GET /api/tasks/{id}`, `PATCH /api/tasks/{id}/status` — and `scripts/contract/tasks-api.json` carries twenty cases for `PATCH /api/tasks/{id}/status` alone, of which six are the 409s that make a move a refusal. Two clients send it: `apps/web/src/features/tasks/api.ts` and `services/mcp-server/src/adapters/http-task-gateway.ts`. The view also showed the assistant returning `409` for a move it had already refused locally, which `services/mcp-server/src/application/task-tools.ts` prevents by reading the task and checking the transition against the status it read: an unknown status is refused with no call at all, a forbidden transition for the cost of one `GET`, and `move` is never called (`moveTask` is `parseStatus` → `getTask` → `checkTransition` → `move`).

Measured against that model, all six rules in `architecture/rules.mjs` returned zero findings, `likec4 validate model` exited 0, and `architecture/test/model.test.mjs` passed twice. They had to. Every rule read elements, kinds and relationships. A step's *endpoints* are validated by LikeC4 — the elements it names must exist — but its *label* is free prose, and nothing read one.

The gap is general, not a misprint: a diagram is the document a reader trusts most and the build checks least. `likec4 validate` proves the boxes are joined the way the file says; it cannot know that the route written on the arrow is not one the code serves. The rules that existed were *topological* — they described the shape of the graph. None was *referential* — none held a name in the model to the file that states it, which is the guarantee `scripts/check-facts.mjs` already gives for a module's repeated copies of a stated fact (ADR-0010).

## Decision

Three rules join `architecture/rules.mjs`, and they read a dynamic view's prose and structure rather than only the graph.

- **`routesDeclared`** collects every `METHOD /path` a step of a dynamic view names and fails any that `scripts/contract/openapi.json` does not declare. One statement of the API's surface, read by the check rather than copied into the model, so the diagram and the contract cannot disagree. When no contract is in the checkout — an `--features architecture` selection ships `architecture/` without `scripts/contract` — a route claim it cannot check is **reported**, never passed: "a check that could not run is a failure to report, not a pass" (AGENTS.md). A view that names no route asserts nothing about the HTTP surface and passes.
- **`viewsSaySomething`** fails a dynamic view with no steps and a step with no label. A dynamic view is a scenario; an empty or unlabelled one renders as a diagram that says nothing while satisfying every topological rule, because an empty dynamic view is valid LikeC4. The rule applies only where there is a runtime to narrate: it returns nothing when the model has no relationship from `user` into the product or between two product elements. A selection without a product — `--features architecture` generates one, keeping the `product` system declaration but none of its elements — has no flow a view could show, so an empty view there is the honest one, not a defect. That premise is the same one `runtimeFlowDocumented` needs, so `rules.mjs` states it once, in a helper both rules call.
- **`interactionsAnswered`** fails a step that leaves a built element (`source.kind` is not `actor`, `target.kind` is neither `actor` nor `system`) and is never replied to by a reverse step. This is the sound part of the stricter "every step is backed by a declared relationship", which cannot be enforced here: a response step and a self-call are legitimately unbound in LikeC4's own idiom, and declaring the reverse relationship to bind them would violate `clientDependencies` (`service -> webapp`). `interactionsAnswered` compares endpoints, which LikeC4 validates, not prose, which it does not.

Each rule carries a hand-built `violating` model, so the meta test of ADR-0043 holds it to firing (ADR-0043). `architecture/rules.mjs` keeps `readFileSync` as its only import and reads `scripts/contract/openapi.json` at `../`, the depth of the file it sits in; `routesDeclared` takes an optional reader so a test can supply the contract without touching disk.

## Alternatives considered

- **Ship `scripts/contract` with the `architecture` feature.** Rejected: `scripts/contract` is the contract of the *task services*, and the modules that serve or repeat it already carry it (`go-service`, `ts-service`, `py-service`, `mcp-server`, `web`, `ts-library`). Making `architecture` carry it would put a second copy in every generated project that selects the model without a service, and a copy is what ADR-0010 exists to prevent. The rule reports what it cannot check instead, which is the louder and cheaper failure.
- **Record the route on the relationship as LikeC4 `metadata` and read it from the model.** Rejected: a dynamic view's steps carry no metadata — the DSL rejects it on a step, and on the view itself — so the route would have to move onto the static relationships, putting the HTTP surface into the structure that ADR-0049 deliberately keeps steps out of. It also would not help: metadata a model states is metadata a model can state wrongly, and the check would still need the contract.
- **Parse `views.c4` as text in `scripts/check-architecture.mjs`.** Rejected: a second reader of the same file disagrees with LikeC4 the first time the syntax changes. Reading the computed model uses the API the model is already validated by.
- **Make `scripts/contract/openapi.json` the source and generate the view's steps from it.** Rejected: a generated narrative is not a narrative — the point of the view is the decision about which interactions matter and where a refusal happens, which no schema holds.
- **A rule requiring every state-changing route a view names to show a refusal.** Rejected as non-discriminating: on the model that prompted this record the route named was undeclared, so the rule's antecedent was false and it stayed silent — an invariant whose precondition the defect defeats.

## Consequences

- A view naming a route the API does not serve now fails `npm test` in `architecture/` in the same pull request, with the view, the label and the route in the message.
- The rule is only as good as the contract: `scripts/contract/openapi.json` is generated from and held to `scripts/contract/tasks-api.json` by `scripts/check-contract.mjs`, so a route reaches the model's rule only after it reaches the contract — which is the order AGENTS.md already requires of a contract change.
- A dynamic view is now held to three properties it can fail on its own: it narrates something, it labels what it narrates, and what it narrates is answered — the first only where the model has something to narrate.
- `viewsSaySomething` makes an empty `dynamic view` a build failure wherever the model has a runtime flow to narrate. The DSL accepts one, and a project generated without a product has nothing to narrate, so the rule stays silent there; where a flow exists, an empty scenario is a diagram that reads as "nothing happens here" and fails.
- These rules read a view's *routes* and its *structure*, not its *behavioural sentences*. A step saying `refuses locally, the service is not called` is held only to being answered by a reverse step; whether the sentence is true of the code is not checked, and this record's own author wrote one that was false and watched `npm run verify` stay green. A route claim has a single file to be held to (`scripts/contract/openapi.json`); a sentence about *when* something is refused has none, so holding it would need a claim the code states in a file a rule can read, not a new reader of prose.
- The step-count of a view is now a fact a reviewer can compare with its title. A title promising every client and its refusal, on a view that keeps one step in a generated project, is a claim the model makes and the generated project cannot keep — the reason the view is titled for what survives in every preset that ships `architecture/`.

## Enforcement

`architecture/test/model.test.mjs` (`npm test` in `architecture/`, part of `npm run verify`) runs every exported rule against the real model and every `violating` model against its rule. On the model ADR-0049 introduced, `routesDeclared` reports nine findings and the test fails; on the model this record ships with, all nine rules return nothing and all four tests pass. With `scripts/contract` removed from the checkout, `routesDeclared` reports the routes it cannot check rather than passing silently. `viewsSaySomething` is held both ways: one test fires its two arms separately, so neither hides behind the other's evidence, and another runs every rule against a model with no product and no flows, which must return nothing. `architecture/rules.mjs` is the only place the three rules are written, and `architecture/README.md` names them.
