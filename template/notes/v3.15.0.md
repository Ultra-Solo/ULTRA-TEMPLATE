## A self-upgrade gate, bounded by a written plan

This release adds the self-upgrade gate: `data/plan.md`, the written record of which invariant check the repository may repair on its own and the evidence that it did; `scripts/check-plan.mjs`, which validates that record and runs as the `chassis: plan` step of `scripts/verify.mjs`; and `scripts/search_replace.mjs`, the matcher a repair is computed with.

The gate is deterministic, and that is the whole point of it. The matcher is the five-pass surgical matcher from Mayo's self-improving maintenance engine, ported as a pure function — a strict contiguous block, a whitespace-tolerant block, a pass that skips truncation artifacts, a unique-substring match above five characters, and a single-line anchor — behind a catastrophic-edit guard that refuses any edit removing more than `max(25, 30% of the file)` lines. No model drives it: a model's output is not reproducible, so nothing about it could be verified the way every other check here is verified. An earlier attempt at this modeled the loop on Mayo's engine with a model applying the matcher; the matcher is the part worth keeping, and it is now the part that ships.

What the gate may write into itself is bounded to what `data/plan.md` declares self-upgradeable: the registration of an upgrade job in `.github/workflows/verify.yml` and the two gate scripts. Everything that states a shared rule — the task rules, the contract, each module's `module.json`, `scripts/verify.mjs`, the hygiene rules, `scripts/modules.mjs` — is repaired only by a minimal pull request computed with the same matcher and subject to the same caps. ADRs, `scripts/configure-github.mjs` and the `.github` ruleset are never self-upgradeable: they are written only by a human review of that pull request.

Three rules matter to anyone editing this template:

- The gate is a chassis step, not a new CI job. The one-required-check rule is untouched, and neither `verify.needs` nor `scripts/configure-github.mjs` needs a change. Wiring an `upgrade` job later means listing it under `verify.needs` in the same change, or GitHub refuses to start the run.
- An entry's evidence lines must be indented exactly four spaces under the field and each must begin with `PASS`, `FAIL`, `COMMIT`, `CI`, `PR` or `CLONE`. A line indented less is not read at all, and the entry then fails as one with no evidence — which is a schema error the plan's own checker reports, not a silent pass.
- `data/plan.md` is validated on every run, in this repository and in every generated project. It ships as a worked example: a generated project inherits it unchanged, passes `chassis: plan` with it, and its first cadence check rewrites it for its own checks, exactly as that project writes its own standing plan.

Nothing has to be installed or configured to adopt this. The gate runs wherever `scripts/verify.mjs` runs, so it runs in CI, in a generated project, and on a contributor's machine with the same verdict. The template version advances to **v3.15.0**.

The matcher is linear on the text it reads. Its truncation-artifact pattern recognises a comment-only ellipsis with character classes rather than nested alternatives, so a line of slashes cannot make it backtrack; `test/search_replace.test.mjs` holds it to a time bound that a backtracking pattern fails in seconds.
